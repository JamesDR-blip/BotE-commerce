## Evidence boundary

The project owner confirms there has never been a production or staging deployment, database, or production data. This is first-production provisioning. PostgreSQL 16 has been verified as a local runtime in earlier evidence, but no operation was performed against it for this phase. The full suite baseline supplied for this phase is 992 passed; tests were not run here.

The evidence sources are the current SQLAlchemy declarative metadata (`database/models.py`), the 23 files in `database/migrations/versions`, repository call sites, tests, and prior recorded PostgreSQL 16 failure evidence in [PHASE_5A_MIGRATION_FORENSICS.md](PHASE_5A_MIGRATION_FORENSICS.md). `database/migrations/env.py` uses `Base.metadata` as Alembic target metadata. Development/test code and many tests call `Base.metadata.create_all()`; this is evidence about those startup/fixture paths, not the authoritative production schema or a substitute migration plan.

No Alembic upgrade, downgrade, stamp, `create_all()`, SQL, or database connection was run. Runtime consumer/test evidence below is static repository inspection. A test that creates SQLite tables from `Base.metadata` proves behavior under that fixture, not PostgreSQL DDL compatibility or migration completeness.

## ORM metadata inventory

`database.models.Base.metadata` currently contains 31 tables. The complete table/column/type/nullability/default/PK/FK/unique/index inventory is recorded in [FIRST_PRODUCTION_PROVISIONING_ASSESSMENT.md](FIRST_PRODUCTION_PROVISIONING_ASSESSMENT.md), section “Current ORM table inventory.” That field-level inventory is the ORM evidence referenced by each row below.

Metadata-wide observations:

- Types are SQLAlchemy generic `String`, `Integer`, `Float`, `Boolean`, `DateTime`, `Text`, and `JSON`; no native enum is declared. Of the current DateTime columns, 26 declare `timezone=True` and six trace timestamps declare `timezone=False`: `execution_traces.{started_at,finished_at,created_at}` and `capability_execution_traces.{started_at,finished_at,created_at}`. PostgreSQL type rendering has not been verified here.
- Metadata declares Python-side defaults (`Column.default`) for multiple fields. It does not make those server defaults. No `server_default` contract was found in the ORM inventory.
- Primary keys are mostly `VARCHAR(36)` strings; `reports.id`, `validation_logs.id`, and `risk_policies.id` are integer autoincrement keys. PostgreSQL sequence/identity behavior needs verification.
- ORM relationships include explicit `cascade="all, delete-orphan"` for organizations→memberships/quotas, roles/permissions→role-permission links, users→workspaces, workspaces→projects, projects→datasets/workflows, workflows→versions/executions, workflow executions→capability traces, executions→reports/logs/traces, and ChangeSets→items. These are ORM unit-of-work behaviors, not database `ON DELETE CASCADE` clauses. The tracked ORM/migration evidence does not establish a broad database cascade policy; tests must distinguish ORM deletes from direct SQL deletes.
- ORM declares no `CheckConstraint`. State/category fields are strings. Unique constraints include roles.name, permissions(resource, action), role_permissions(role_id, permission_id), memberships(user_id, organization_id, role_id), organizations quotas, compliance policies, channels, datasets mappings, sync idempotency/attempt number, workflow version, and others detailed in the inventory.
- The current model source at `database/models.py:225` and `0001_persistence` both declare `users.email` unique; the ORM additionally declares an index. This inspection corrects the prior assessment's statement that current ORM metadata lacked uniqueness. The exact physical index/constraint representation still needs PostgreSQL comparison, but the logical uniqueness contract is corroborated by both current sources.

### Matrix conclusions

- Missing creators in the connected Alembic history: `projects`, `datasets`, `workflows`, `workflow_versions`, `workflow_executions`, `execution_traces`, and `capability_execution_traces`. `d14c1f2a9b31` is the first revision that references `datasets`, but it only alters that assumed table.
- `users`, `executions`, `validation_logs`, and `reports` are created by conditional branches in `0001_persistence`; a pre-existing partial schema can skip related objects/indexes, so conditional creation does not guarantee reconciliation.
- The current ORM and historical DDL are not a PostgreSQL-tested equivalent. The current ORM declares some values as Python defaults, while migrations may encode server-side defaults or may omit them. The target must decide which writer behaviors are required.
- No migration-created table was found that has no current ORM table mapping. Conversely, there are seven current ORM tables with no creator. Migration-added columns and integrity transformations also need field-level reconciliation even when the table exists.
- No database check constraint/native enum/extension was evidenced in the ORM declarations or migration files inspected. This finding is bounded to tracked source, not external infrastructure.

## Canonical target decision

**`CANONICAL_TARGET_SCHEMA = NOT_YET_DEFINED`.** The 31 ORM table declarations are a candidate inventory, not an approved database contract. The current Alembic chain is also not a valid definition because it is incomplete and internally conflicting. The evidence matrix therefore records gaps instead of silently selecting either source.
